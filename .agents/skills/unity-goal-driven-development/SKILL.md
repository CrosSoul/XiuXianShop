# Unity 目标导向开发

以当前玩法目标和验收结果为边界，完成必要实现与验证。用户负责玩法目标和设计取舍，Codex 负责合理技术实现；不要求策划 prompt 指定类、架构或代码步骤。用户当前明确指令优先，本 Skill 补充项目 AGENTS.md，不扩大授权范围。

## 1. 先理解问题，再作决定

- 先读任务相关的 Docs、代码及必要的 Unity 状态，区分设计意图、已有实现和已验证结果。文档中的计划、旧验收记录和背景描述都不是当前功能已完成的证据。
- 将目标理解为玩家可观察的行为及验收结果。多步任务简要说明里程碑和验证方法；简单修改直接推进，不为每次改动生成长计划或问卷。
- 小的实现选择、可逆默认值和普通技术问题自主判断。简短记录影响结果的假设和取舍；发现更简单的可行方案时采用或说明理由，不把技术选型交回策划。
- 只有尚未获得授权、会显著改变玩法方向、可能破坏已有内容或需要产品取舍的重大歧义才暂停相关工作，说明影响与建议并请求决定；继续不依赖该决定的工作。已明确的选择不重复确认。

## 2. 简单方案，但完成整个目标

- 选择能让当前玩法目标完整工作的最简单可读方案。自主补齐必要输入、反馈、状态转换和真实边界情况；不能以用户未逐项点名为由留下按钮无效、失败路径损坏状态或闭环无法继续的半成品。
- 例如当前任务涉及空间物品或交易时，按实际需要处理旋转/翻转后的占格、越界或重叠失败回退、归属、资金与重复结算。这些是判断必要边界的例子，不是每次都实现一套系统，也不表示项目已实现它们。
- 不为了未来扩展预建框架、抽象层、通用配置或新玩法。不因“少写代码”压缩可读性，也不因行数目标重写已工作的系统；需要策划调整的参数仍按项目规则暴露。
- 先沿用现有实现和风格；只有当前目标确实需要时才提取复用或局部重构。不要为不可能发生的状态堆砌防御分支，也不要省略实际可达的失败路径。

## 3. 精准修改，保护 Unity 内容

- 每项修改都应能解释它如何服务当前目标或防止本次回归。先区分 Git 已有改动，只清理本次修改造成且确认无引用的冗余；无关旧问题记录即可，不顺手格式化、重命名或重构。
- 遵守 AGENTS.md 的 Unity 资产操作规则，保留场景、Prefab、资源的 GUID、.meta、序列化值与引用。修改序列化字段或组件前检查 Inspector 数据、Prefab 覆盖及调用关系，必要时提供保值迁移并验证引用；不能仅凭 C# 没有调用就认定 Unity 回调、按钮绑定或资源可删除。
- 当前目标需要改动资源时，使用 Unity API、Editor Script 或可用 MCP；不要通过重建场景、Prefab 或 .meta 来规避理解现有引用。工程设置与 Package 变更仍受项目范围约束。

## 4. 以证据推进到约定里程碑

- 按“实现 → 针对性验证 → 修复”持续推进当前已授权目标，不在计划或第一个成功路径处结束。非阻塞问题自行处理或记录；需要外部条件时明确真实阻塞，不无限重复同一失败操作。
- Bug 修复优先复现问题，必要时补能捕获回归的测试；复用适当的现有测试。验证规模与风险相称，不为文案或简单可逆修改建立空测试框架，也不把所有任务强制改成测试先行。
- 按项目规则检查 Console、Editor ready、编译及 Domain Reload 状态，不清空日志掩盖问题；区分既有与本次问题。工具不可用时做可用检查，记录缺失证据，不能假称检查通过。
- 汇报时明确证据层级：静态检查/编译、自动测试（注明 Edit Mode 或 Play Mode）、Unity 中实际运行的场景与操作、玩家人工试玩。自动 Play Mode 可以证明实际运行过所测路径，但不能替代人工试玩、操作手感或全部玩法验收。
- 对未运行的玩法路径给出具体手动步骤和预期结果。按 AGENTS.md 更新 DEVLOG，记录实际改动、验证结果、重要假设及遗留项；长任务保留当前里程碑和下一步以便续接。完成已授权里程碑后不自行开始计划中的后续玩法。
