## 2. 日历窗口

主界面提供清楚的日历入口，点击打开窗口，能够关闭并返回经营界面。

窗口需要：
- 显示连续两周、共14个游戏日，每周7格。
- 明确显示当前日期，并在对应日期格标记“今天”。
- 显示收租日及合理可见的租金信息。
- 显示市场事件名称、日期范围和状态。
- 能查看相邻两周，并返回当前日期。

两周按连续游戏周展示，周起点与日期编号沿用现有规则，不另造独立时间体系。不要加入现实年月、固定72天终局倒计时或新剧情。

**收租必须来自实际经营状态。**保留现有收租周期、首期金额、递增与结算约定；打开、关闭或翻阅日历不能触发收租，也不能造成重复扣款。

## 3. 市场事件

每个游戏周**大约出现2–3个市场事件**，每个持续**1–3天**。本阶段只需少量可重复的事件类型，不要求大量内容。

每个事件应有：
- 名称、简述
- 开始日、结束日、持续天数
- 受影响的商品类别
- 适用交易方向
- 价格标签及百分比效果

事件以游戏日期为准。未来事件可以显示，但未到开始日不能影响价格；结束后效果失效。

已确定的事件安排不能因为打开日历而重抽。重复查看、睡觉和存档恢复不应造成事件重复生成、重复生效或日期错乱。

### 持续条布局——重点

事件要用**跨日期格的持续条**表示持续时间，而不是只在开始日放一个图标。

必须保证：
- 同一天两个或更多事件，各占独立显示行，持续条不叠在一起。
- 部分重叠的事件仍然清楚可辨。
- 跨周事件正确分段显示，不错误穿越整行。
- 只覆盖部分可见日期的事件显示正确。
- 长名称可缩略，但能查看完整名称、日期与效果。
- 日期数字、今天标记、租金标记和事件条互不遮挡。

请提供一个**固定的重叠事件测试情景**，让我回来后可以直接看到至少两个事件在同一天持续，而不是依赖随机碰运气。

## 4. 价格标签必须进入真实交易

沿用已确认规则：

**当前预估价值／报价 = 基础价值 ×（1 + 当前有效价格标签百分比修正之和）**

正负百分比先求和，再作用于基础价值。玩家出售默认零售加价为 **+15%**。市场事件提供额外标签，不得直接覆盖基础价值，也不要另做一套独立市场报价。

验收要求：
- 只影响指定类别与交易方向。
- 不匹配的商品不获得事件修正。
- 同一天多个有效事件能够同时参与计算，不互相覆盖。
- 玩家能在相关价格详情中看到有效标签及其百分比。
- 商品详情、交易单价、总价、预算判定、确认状态与实际成交金额一致。
- 日期变化导致标签开始或结束时，报价正确刷新；不能显示旧价却按新价结算。
- 历史购买价值保留当时实际成交金额，不随未来行情重算。
- 保留类别＋预算、连续成交、展示柜开业快照和三区域搬运等现有规则。

### 可控价格测试

以下仅为**测试数据**，不要求成为正式商品或市场平衡：

| 情景 | 预期报价 |
|---|---:|
| 基础20，仅玩家出售+15% | 23 |
| 基础20，出售+15%，市场+20% | 27 |
| 基础20，出售+15%，市场-20% | 19 |
| 基础20，出售+15%，两个市场标签+20%与-10% | 25 |
| 基础20，玩家买入，适用+20%且无其他修正 | 24 |

还需验证：不匹配类别／方向不生效；未来与过期事件不生效；多件报价求和与预算、结算一致；市场切换不改写历史购买价值。

价格取整、极端负修正下限、同名标签去重等仍有未定边界。保留现有规则，用无取整歧义的数据验证，不要擅自把临时行为升级为正式设计。

## 5. 内容与范围

可制作少量有辨识度的事件，例如丹药需求增加、灵材供给变化、法器行情变化。具体名称与数值由你根据现有商品选择，确保实际可测试。

这些是**可调整原型配置**，不是最终经济平衡。不要加入复杂供需模拟、通胀、声望联动、生产效率、随机品质、新产业、战斗、秘境、黑市或终局剧情。

不做大规模主界面重构、正式像素美术、复杂动画或无关架构重构。界面可以临时，但必须清晰可读。
