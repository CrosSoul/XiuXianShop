# 修仙当铺｜下一轮 Codex 自主开发任务 v3

## 本轮目标

请在当前 Unity 2D 项目中，连续推进到一个**可以完整体验一天营业的交易切片**。这不是要求你再做一轮孤立功能演示，也不是要求一次完成整款游戏。最终应让玩家从整理库存开始，开门接待顾客，完成买卖、连续交易和下一位顾客操作，结束营业，查看简要结算，并能进入下一天继续测试。

优先解决当前测试版的两个核心问题：**已有基础逻辑尚未形成完整营业体验；缺少视觉参考导致界面粗糙。** 分辨率问题已有 Codex 修复报告，本轮只做必要回归，不再重新排查已解决的问题。已实现的功能应先复核并复用，不要因为本任务重新造一套。

我将使用 Codex 的目标模式执行本任务，期间可能约 8 小时无人值守。请在本轮可用执行时间内自主检查、实现、验证和修正；不必每完成一步就停下来询问。目标达成后停止扩展，不要为了填满时间增加新系统。

## 二、优先级与里程碑

### M0｜确认当前基线并复用显示修复

已记录的修复方式是关闭 Unity Game 视图的 Low Resolution Aspect Ratios，使预览恢复原生分辨率。该选项属于个人 Editor 布局，不保证随 Git 同步到其他电脑。若当前环境仍未应用，按已有说明恢复即可。

本轮只需在进入 Play Mode 后快速确认中文文字清晰、Game Scale 正常、关键按钮与拖放可用。若无回归，直接进入 M1。仅在出现可复现的新问题时重新排查，并记录实际原因。正式界面的小字号和布局适配仍属于 M3，不与已解决的预览分辨率问题混为一谈。

### M1｜把商品价值、物品管理与交易规则复核为可靠闭环

**先完成 G-05 商品价值与报价的增量改造，再将其接入交易闭环。** 用户已明确不再采用只有固定收购价／出售价的完整价格模型。以正式 GDD v0.2 为依据，保留现有有效数据与功能，不为了改字段而重做整个物品系统。

商品价值至少区分：不变的基础价值、当前预估价值／本次报价、玩家实际买入时记录的购买价值，以及影响报价的有效价格标签。直接获得的物品不显示购买价值。仓库中尚未进行交易核算时，预估价值等于基础价值；进入谈判柜台的交易上下文后，显示当前交易预期价值。

**已确认的计算关系：**
`预估价值 = 基础价值 × (1 + 所有当前有效价格标签的百分比修正之和)`

玩家物品出售时默认添加“零售加价（+15%）”；市场事件可以附加对应价格标签。修正先求和，不要擅自改成逐项相乘。基础价值20、仅有+15%时应得到23；同时有+15%与-30%时，未取整结果为17。后一个只是公式测试，不代表原版已有该组合。

本次报价必须与详情、交易清单、总价、预算判定和实际成交金额一致。购买价值保存当时实际买入金额，不随日后估值变化重算。旧收购价／出售价可作为迁移过渡，但不能与新报价形成互相矛盾的价格真相。

取整、价格下限、极端负修正、重复标签、买卖双方修正差异仍未定案。确需实现时采用最小、可替换、可测试的临时处理并记录；不自行设计完整市场经济。保留现有可用的买卖逻辑，避免让价格重构破坏库存或货币结算。

**新增验收：**
- 基础价值20的商品在仓库显示预估20；进入玩家出售场景且仅有+15%时显示报价23，基础价值仍为20。
- 有效正负标签变化会重新计算报价；基础价值不被覆盖。未取整测试使用20、+15%、-30%，结果17。
- 玩家以16买入物品，购买价值记录16；之后估值变化，历史购买价值不变。直接获得的物品不显示购买价值。
- 多件商品按各自本次报价求和，预算判定和实际成交金额使用相同总价。
- 物品详情能区分基础价值、预估价值、购买价值（若有）与有效标签；交易详情能显示修正项、单价及总价。



所有可摆放物品拥有自己的形状和类别 tag，支持手动旋转／翻转；空间合法性与交易合法性必须分开。展示柜、谈判柜台、底部物品栏在营业前后都能自由搬运。谈判柜台不能根据顾客预设的具体商品实例限制放入物品。

顾客的核心模型为“求购类别 + 当前剩余预算”，不是固定购买计划。符合类别且本次报价总和不超过预算时允许确认；同一顾客可以连续成交，每次扣减实际成交金额。玩家可主动进入下一位顾客。

必须复核下列既有案例：
- 预算20，出售本次报价18的回气丹，成交后剩余2。18为指定测试报价，不代表固定基础价值。
- 预算40，连续出售两颗本次报价18的回气丹，预算依次为22、4；第三颗提示资金不足，不能确认。
- 预算60，一次放三颗本次报价18的回气丹，显示总价54并允许成交。
- 三个独立实例都能单独放入谈判柜台；不能只允许第一件。
- 类型不符时仍可合法放置，但确认出售禁用并提示原因。
- 未成交、仍有预算时，也能主动换下一位顾客。
- 营业后可以把展示柜和谈判柜台物品搬回物品栏，开业后的展示柜变动不重新计算本轮吸引效果。

对于空柜台、混合类别、错误提示优先级等尚未定案的边界，先采取一致、保守、可测试的临时处理，明确标记为本轮实现选择，不要声称是原版规则。

### M2｜形成真正的一天营业流程

以现有系统为基础串起以下体验：

**整理库存 → 开始营业 → 生成本日客源 → 顾客到来 → 玩家购买或出售物品 → 连续交易／下一位顾客 → 结束营业 → 简要结算 → 下一天。**

参考白板已经区分买家和卖家：可售物品吸引对应类别买家，广告牌类物品吸引对应类型卖家；买家类别按展示柜中总价值最高的单一可售类别决定，商品总价值与顾客携带金额相关。具体生成公式、并列类别和空柜规则仍未定案。此处的展示柜“价值”如何接入动态估值仍须以 GDD 的客源规则为准，不能自行把历史购买价值当成吸引权重。请保留现有已可用规则；需要补足时使用少量、可调整、可重复测试的临时参数，不把临时参数写成正式原版公式。

本轮至少要能完整测试一位买家与一位卖家。卖家能够提供物品，玩家能够查看并确认购买，购买后物品进入可管理库存，货币和库存发生正确变化。买家使用已确认的类别与预算规则。不得出现重复成交、物品凭空复制、扣款失败却取得物品、出售后仍可再次出售同一实例等问题。

顾客自然结束与玩家主动跳过都要有明确状态。白板记录“无顾客时单击呼叫下一位；有顾客时长按约1秒可遣散并呼叫下一位”。若现有正式交互尚未采用这一输入方式，可先保留清晰可见的主动下一位操作，同时记录与原版交互的差异；不要为了模拟长按而牺牲可用性。展示剩余顾客数，并让营业结束具备可理解的入口与反馈。

结算只要求本轮最小结果：本日收入、支出、余额变化及进入下一天。租金、服务开销、市场事件的完整生成与持续规则、剧情顾客限制和长期成长尚未完整定案，不要擅自扩展为正式经济系统。若已有功能可安全保留，不必删除；新补充的规则必须明确是临时测试设计。

### M3｜让这个闭环拥有可用的正式界面骨架

当前版本缺少视觉参考，不能再只为验证代码而随意排布。请以用户提供的主界面、交易详情和相关截图为依据，整理主界面信息层级和交互区域；优先保证三个格子区域、顾客信息、预算、待售清单、价格修正、总价、错误提示、确认交易、下一位顾客及营业状态易于辨认和操作。物品详情至少能区分基础价值、预估价值、购买价值（适用时）、标签与简述；交易详情应展示吸引原因、修正项、单价和总价。

白板记录主仓库24×10、谈判柜台18×4、展示柜7×5。这些是参考游戏的格子尺寸，不自动等于修仙版最终定案。若正式规格尚未确认，优先保留当前项目已有数据与适配能力，不为了照搬尺寸而破坏现有库存。不要把参考截图整张当作不可交互背景来替代正式 UI。

本轮目标是**可用、清晰、结构正确的界面骨架**，不是最终美术完成。不要求制作大量美术资产、动画、装饰或完整设计系统。缺少精确参考的局部使用克制的占位设计，并记录待补视觉规格。

### M4｜完整回归与交接

在实现过程中持续验证，而不是最后一次性发现全部问题。完成后至少执行可用的自动化检查、Unity 编译/进入 Play Mode 检查、显示修复回归、G-05 价格案例、关键交易案例及完整营业日流程。能够实际操作的项目应提供可重复的测试入口或测试数据。

交付报告应包含：实际完成范围、未完成范围、关键测试结果、已知问题、使用的临时设计假设、修改文件概要，以及本地提交信息（若有）。任何测试未执行时写“未测”，不能写“通过”。此前显示修复报告指出测试列表有7项但实际执行0项，不能沿用为7/7通过；本轮若仍无法运行，记录原因并继续其他可验证工作。
